# 前缀模式:多面板共享同一 /64 时的地址碰撞与"盐值"方案

状态:**待解决 / 设计草稿**
范围:IPv6 **prefix 模式**的地址分配(不含 pool 模式)
性质:本文是调查记录 + 方案思考,不是已实现功能

> 记号约定:本文用符号表示地址,不出现任何真实前缀或地址。
> `P::/64` 指某运营商前缀;一个容器的地址块写作
> `P::<salt>:<index>:0/112`(salt、index 均为十六进制)。

---

## 0. 摘要

- 面板给每个容器分配一个 **/112 块**,由「配置前缀 + 32bit 块索引 + 16bit 主机位」拼成。
- 历史上块索引由 **`sha256(用户名)[0:4]` 派生**,这使得同一 /64 下两台面板、同名用户会拿到**逐字节相同**的地址(确定性碰撞),并有隐私问题。
- 现版本已改为**每账号随机 32bit 索引并入库**,确定性碰撞已消除;但**多台面板共享同一个 /64** 时仍存在概率性碰撞。
- 本文提出用设计上**空闲的 16bit** 做一个可配置的「盐值」,把跨面板碰撞概率再降 2^16,并讨论了它的边界、实现坑,以及一个比"加熵"更该补的手段:**创建时的地址探测**。

---

## 1. 背景

### 1.1 地址布局

一个容器的 /112 块在 128bit 地址里的布局是:

| 位区间 | 用途 |
|---|---|
| `0 .. prefixlen-1` | 配置的前缀 |
| `prefixlen .. 79` | **空闲**(设计之初就留空,未被使用) |
| `80 .. 111` | 32bit 块索引(每账号一个,存库) |
| `112 .. 127` | 容器自己的 16bit 主机位 |

空闲位的数目 = `80 - prefixlen`,于是:

| 配置前缀 | 桥使用 | 空闲位 |
|---|---|---|
| `/48` | 前缀里的**第一个 /64** | 32 |
| `/56` | 第一个 /64 | 24 |
| `/60` | 第一个 /64 | 20 |
| `/64` | 该 /64 本身 | **16** |
| `/65` .. `/79` | 前缀本身 | 8 .. 1 |
| `/80` | 该 /80 本身 | **0** |

这就是"盐值"能落地的物理依据:在 `/64` 上有 16bit 死位可用,在 `/80` 上一位都没有。
(桥固定使用前缀的第一个 /64,容器地址也都落在第一个 /64 内,所以即使在前缀短于 /64 时,盐值放在 bit 64..79 也仍然在桥的 /64 覆盖范围内。)

### 1.2 为什么会撞

- **旧实现(确定性)**:块索引 = `sha256(用户名)[0:4]`。这是一台机器之外的**全局常量**——同一 /64 下的两台面板,只要用户名相同,块就完全相同;双方会同时宣告同一个地址。顺带,地址后缀暴露了所有者(可用用户名枚举反推)。
- **现实现(概率性)**:每账号创建时随机取 32bit 索引,存入 `users.ipv6_index`,并对该列建 `UNIQUE` 索引作为兜底;分配循环会重试。同一台机器内由唯一索引保证不撞;跨面板则退化为概率问题(见 §3)。

### 1.3 触发场景

当两台或多台面板的容器出现在**同一个 /64** 里时,跨面板碰撞才可能出现。这种部署是真实存在的(见 §2.4)——运营商把某段按"在线直连"方式投递时,多个主机会共享同一段。

## 2. 调查结论:面板现在是怎么处理前缀的

### 2.1 前缀从哪来

安装期由网络询问脚本交互得到(或用环境变量注入),重装时沿用现有配置。交互路径会先跑一个探测脚本,只解析它的判词行:

- 判为"整段已路由" → 走 prefix 模式,候选前缀**默认取自本机自己的全局地址**(即本机 SLAAC 所在的那一段),用户回车即用;
- 判为"未验证" → 提供 pool / 手工输入前缀 / 关闭 三种选择;手工输入被明确当作"信任用户输入"。

### 2.2 配置层校验什么

配置读取后,唯一的校验是**语法性质**:必须带前缀长度、可解析、是全局前缀(非 ULA/链路本地/回环)、长度 ≤ /80。
**不校验任何与路由方式有关的东西。**

### 2.3 运行期机制

- 桥(`incusbr0`)按前缀配置:`ipv6.address=<网关>/<min(prefixlen,64)>`、`nat=false`、`routing=true`、`dhcp.stateful=true`,并加一条 `<前缀> dev <桥>` 路由;
- 桥网关取前缀内第一个空闲地址,挑的时候会避开本机地址、默认网关、以及邻居表里已出现的地址;
- 每个容器:设备上设 `ipv6.address=<块>::1` 与 `ipv6.routes=<块>::/112`,把整块路由进容器;容器内静态绑 /128 并把整块设成 local 路由;
- 一个 NDP 响应器在**外网卡**上对配置前缀内的邻居请求作答(它遍历的允许集合就是配置前缀);
- 开机 / 安装 / 重装时从数据库重建以上全部。

整套模型**默认"配置前缀已经路由到本机"**,代码注释也是这么写的。

### 2.4 关键结论:面板无法判定"独享 vs on-link"

- 唯一的"分类"发生在安装期,方法是:**在前缀里随机取一个地址绑到本机,再从外部探针 ping 它**。
- 这个测试测到的性质,**恰好是"独享"和"谁声明谁用"两种情况共有的**:独享靠运营商的一条路由送达;on-link 靠路由器发邻居请求、本机回邻居通告送达。两种都会判为"已验证"。
- 实测中观察到两个佐证:同一台机器上,既能"验证"一个独立路由的段,也能"验证"本机自身 SLAAC 所在的段;而且每次探新地址时**第一次常常全丢、重试就通**,这正是 NDP 的学习过程,而非路由的建立。
- 另有一个值得注意的副作用:交互安装的**默认候选就是本机自身的 /64**(即上游 on-link 段)。照默认走,容器会被放到运营商的 WAN 段上。

**结论**:主机侧没有一个可靠方法能判定前缀是否独享,面板当前也没有做这件事。它只能证明"前缀内的地址绑到本机后从外部可达"——而共享段同样满足这一点。因此,**多台面板共享同一 /64 是一种必须正视的部署形态**,碰撞问题值得专门处理。

## 3. 碰撞量化

设共享段内面板 A 有 N₁ 个容器、面板 B 有 N₂ 个容器:

- **旧实现**:同名即必撞;即便不同名,派生空间也只有 32bit,B路碰撞概率约 `N₁·N₂ / 2³²`。
- **现实现**:随机 32bit 索引,跨面板概率仍约 `N₁·N₂ / 2³²`。
- 参考量级:两边各 100 个容器时,`100·100/2³² ≈ 2.3×10⁻⁶`。
- 若再把空闲的 16bit 用作盐值,概率降到约 `N₁·N₂ / 2⁴⁸`,即 `≈ 3.6×10⁻¹¹`,再降 2¹⁶ 倍。

**判断**:确定性碰撞(真正的 bug)已被随机索引修复;剩余概率在任何合理规模下都已经可忽略。盐值是一个**廉价的顺带优化**(用的是死位),但**不是**消除碰撞的关键手段,更**不是**安全或隔离机制(共享段里任何人都能宣告任意地址,见 §6)。

---

## 4. 方案:每安装一个可配置的 16bit 盐值

### 4.1 定义

在配置里增加一个 16bit 盐值 `net.ipv6_salt`:

- 地址块变成 `P::<salt>:<index>:0/112`,即盐值占据 bit 64..79;
- **只对新创建的容器生效**;已存在的容器地址不变;
- 默认值:当配置前缀 ≤ /64(有空闲位)时为**随机值**,否则为 `0`;
- 用户可随时修改;修改后老容器仍用它们各自创建时的盐值。

### 4.2 存储:索引字段从 32bit 扩展到 48bit

要让"改盐只影响新容器",盐值必须**随账号一起存下来**(不能只存配置里,否则改配置会移动所有老地址)。因此把每账号存储的索引扩为 48bit:

```
存值 = salt(16bit) << 32 | index(32bit)
```

落位:把该 48bit 值大端写入地址的 **bit 64..111**(即字节 8..13;其中字节 8-9 是盐,10-13 是索引)。当前实现是 32bit 写进字节 10..13,因此这是一次**写位范围**的调整。

要点:

- **不需要改数据库 schema**:`ipv6_index` 列本就是 SQLite 的 8 字节整数,48bit 放得下;变化的只是它的**语义**。
- **旧数据零迁移**:老行的值本来就是"盐=0"的那 32bit,天然兼容,不需要 UPDATE。
- `0` 仍然表示"无索引"(pool 模式 / 纯 v4 容器),哨兵语义不变(只有 `salt=0 且 index=0` 才是 0,而该块是网关所在的块,本来就不会被分配)。

### 4.3 一个关键洞见:盐值 + 32bit 随机 ≡ 48bit 全随机

对**跨面板的成对碰撞**来说:

- 方案「盐(16 随机)+ 索引(32 随机)」的概率
  = `P(盐相同)·1/2³²` = `2⁻¹⁶ · 2⁻³²` = `2⁻⁴⁸`
- 方案「48bit 全随机(每容器)」的概率 = `2⁻⁴⁸`

**两者完全等价。** 即:盐值**并没有比"直接用满 48bit 随机"带来更多熵**。

那么盐值的真正价值是什么?——**它是一个可协调的旋钮**。如果两台面板的操作者知道彼此共享同一个 /64,就可以给两边设**不同的盐**,从而**确定性地**把地址空间分开,而不是靠概率。这个价值只在"能协调"时兑现;陌生人之间协调不了,那剩下的就只有熵,而熵靠随机就够了。

因此本方案的定位应当是:**默认随机 + 可手动修改**,而不是"默认 0、按需设置"。

### 4.4 盐宽度的通用规则(不要只区分 /64 和 /80)

规则应是 `saltBits = min(16, 80 - prefixlen)`:

- `/64` → 16bit,正好用满;
- `/80` → 0bit → **盐必须为 0**;
- `/65 .. /79` → 只有 `80-prefixlen` 位可用,**盐的高位会写进网络前缀**——必须要么强制为 0,要么按可用位掩码;这是最容易出错的边界。

建议:配置写入时校验"盐的越界位必须为 0",不合法则拒绝(而不是静默截断),这样 `P::/80` 这类云上探测到的切片不会因为设了盐而把前缀写坏。

### 4.5 实现清单(代码位置,仅供参考)

- 配置项:`net.ipv6_salt`(可参照 `net.ipv6_subnet` 的注册方式),并新增一个"盐是否适配前缀"的校验;安装期在检测到 `prefixlen ≤ 64` 时随机生成。
- 块构造:把 48bit 写入 bit 64..111(现为写 bit 80..111 的 32bit)。
- 索引分配:候选值改为 `salt<<32 | rand32`;网关块排除逻辑保留。
- 数据库:`ipv6_index` 的**语义注释**更新(列名可保留);老的派生函数保持"盐=0"的行为不变。
- 文档:IPv6 设计文档中补充盐值/位布局一节。

### 4.6 已知的坑

1. **分配去重集合的截断**:现有实现把"已用索引"收集为 `uint32` 集合。扩展到 48bit 后必须按**完整值**比较,否则会误判(不同盐但低 32 位相同的账号会被当成同一个)。
2. **写位范围**:写 48bit 时务必只落在 bit 64..111,别碰网络前缀与主机位。
3. **`0 = 无索引` 哨兵**:扩展后仍需保证"无索引"的唯一表示;盐非零时该值自然非零。
4. **`/80` 与非 16 位边界**:见 §4.4,必须在写入配置时拒绝越界盐,而不是运行时才发现前缀坏了。
5. **不要把它当安全边界**:盐只是**分配建议**,不提供任何隔离或防护。

## 5. 比"加熵"更该补的:创建时的地址探测

盐值把碰撞从"概率很小"降到"概率更小",但**始终是概率**。要把它变成**保证**,应当在创建容器、选定块之后,做一次**线路探测**:

- 对外网卡上该块的**主地址**发一次邻居请求(或短暂绑定并观察重复地址检测结果),在约 1 秒内若收到别人的邻居通告,就换一个索引重试;
- 面板已经有 raw-socket 的 NDP 响应器,加一个"探测"函数成本很低。

能抓到:另一台面板**在线**的容器、被 squatted 的地址、路由器占用的地址。
抓不到:对端容器**不在线**时的占用;以及"现在没人用、以后被接管"的情况(重复地址检测只反映当下,不阻止将来被抢占)。

定位建议:这是对碰撞的**真正兜底**,应当与盐值一起做;如果只能做一件事,探测比盐值更值得。

---

## 6. 盐值覆盖不到的共享 /64 隐患

即使地址块互不重叠,共享同一个 /64 还有别的问题,值得单列:

- **桥网关冲突**:每台面板都会在自己的桥上配一个位于该 /64 内的全局网关地址,而"挑空闲地址"的逻辑只能看到**本机可见**的信息(本机地址、默认网关、本地邻居表),看不到另一台主机桥上的网关;两台可能选到同一个地址,在该 L2 上谁先应答邻居请求谁赢。
- **NDP 响应器竞争**:两台主机的响应器在同一 L2 上为各自容器的 /112 作答。盐值让两边的地址空间不重叠,顺带缓解了这一点——这也是盐值的一个附带收益。
- **前缀是否独享本身**(§2.4):这是比碰撞更根本的问题,盐值完全不涉及。

## 7. 备选方案对比

| 方案 | 跨面板碰撞 | 可协调性 | 成本 | 备注 |
|---|---|---|---|---|
| A. 维持现状(32bit 随机) | `N₁N₂/2³²` | 无 | 0 | 已可忽略;不含保证 |
| B. 48bit 全随机(每容器) | `N₁N₂/2⁴⁸` | 无 | 低 | 与 C 熵等价,少一个配置面 |
| C. 每安装 16bit 盐值(本方案) | `N₁N₂/2⁴⁸` | **有**(可手动分开) | 中(配置 + 位布局 + 校验) | 旋钮是它的卖点 |
| D. **C + 创建时探测** | 有实际检测 | 有 | 中高 | **推荐** |
| E. 前缀短于 /64 时给每安装一个 /64 | 结构性不重叠 | 有 | 高(要改桥模型) | 超出本议题,值得另开 |

## 8. 开放问题 / 决策点

1. **盐宽度**:固定 16bit,还是随前缀放宽到全部空闲位(`80-prefixlen`,上限可设 32)?后者能用满死位,但配置项宽度随前缀变化。
2. **默认值**:默认随机(≤/64)还是默认 0?随机更省事,但要考虑运维看到"两台不一样"时的理解成本。
3. **可见性**:是否在面板/CLI 里显示"每个容器用的是哪个盐",以便排查?
4. **改盐的交互**:是否明确提示"只影响新容器、老容器地址不变"?
5. **探测的开销与误报**:外网卡 raw socket + 约 1 秒延迟,放在容器创建路径是否可接受?还是做成后台校验?
6. **`/65 .. /79` 规则**:强制盐为 0,还是按可用位掩码?
7. **与既有机制的交互**:pool 模式、`vps transfer`(块索引不跨机迁移)是否受影响?
